# VoxDelta

**한국어 상담 통화 감정 변화 분석 (Korean Call Emotion Shift Analysis)**

## 거버닝 메시지

> VoxDelta는 상담 통화에서 **고객의 감정이 언제, 무엇 다음에 달라졌는지**를 오디오 구간과 발화 근거에 연결해 보여준다.
> 감정 레이블을 잘 맞히는 것이 목적이 아니라, **변화 구간을 증거와 함께 제시하는 것**이 목적이다.
> 상관은 말하되 인과는 말하지 않으며, 기본 처리는 전부 로컬에서 일어나고 외부 전송은 사용자가 명시적으로 승인한 구간에서만 일어난다.

한 문장으로: **"감정을 분류하는 도구가 아니라, 감정이 꺾인 지점을 근거와 함께 짚어주는 도구."**

## 이 메시지가 강제하는 규칙

이후의 모든 설계·구현·문서 결정은 아래 다섯 줄과 충돌하지 않아야 한다.

1. **증거 우선.** 모든 모델 출력은 오디오 구간(start/end)과 전사 발췌로 되짚을 수 있어야 한다. 근거 없는 요약 문장은 리포트에 넣지 않는다.
2. **인과 금지.** 리포트 문구는 "사과 응대 이후 회복이 관측됨"까지만 쓴다. "사과가 회복시켰다"는 금지 표현이다.
3. **로컬 우선.** 오케스트레이션·아티팩트·설정·리포트는 로컬에 남는다. 원격 API는 어떤 스테이지에서 무엇이 전송되는지 UI에 표시하고 승인받은 후에만 사용한다.
4. **불확실은 불확실로.** 신뢰도가 낮거나 결측인 결과는 중립값으로 채우지 않고 `uncertain` / 시각적 공백으로 남긴다.
5. **조용한 폴백 금지.** 최신 후보 모델이 실패하면 안정 베이스라인으로 몰래 되돌아가지 않는다. 실패 사유를 기록하고 사용 불가로 보고한다.

## 무엇을 만드는가

두 화자(고객 1 + 상담사 1)로 구성된 녹음 통화를 입력받아,

화자 분리 → 전사 → 역할 확인(사용자 승인) → 고객 감정 7분류 → 상담사 응대 전략 분류 → 감정 변화 계산 → 리포트

순서로 처리한다. 핵심 산출물은 **고객–상담사–고객 3턴 세트(triplet)** 중 고객의 부정감정 강도가 크게 움직인 구간이다.

- `delta ≤ -0.20` → **회복(recovery) 구간**
- `delta ≥ +0.20` → **악화(worsening) 구간**
- 그 외 → 안정(stable)

감정 스키마는 AI Hub 정렬 7분류(happiness, anger, disgust, fear, neutral, sadness, surprise)이고, 대시보드는 이를 운영 상태 4종(satisfied / stable / dissatisfied / escalated) + `uncertain`으로 환산해 보여준다.

## 범위 밖 (Non-goals)

실시간 스트리밍 분석, 공개 배포·계정·멀티테넌시, 컨택센터 운영 연동, 화자 3인 이상 통화, 상담 품질 자동 평가, 파운데이션 음성 모델 자체 학습.

## 현재 상태 (2026-08-25 · 8주 로드맵 W2 진행 중)

| 영역 | 상태 |
|---|---|
| 코어 파이프라인 (8스테이지, 재개 가능, SQLite + 파일 아티팩트) | 완료 |
| 로컬 FastAPI 수직 슬라이스 (업로드·역할확인·재시도·리포트·오디오 스트리밍) | 완료 |
| Fake provider 기반 계약 테스트 | 완료 |
| 실제 provider 코드 (pyannote community/precision, faster-whisper, Qwen3-ASR, XLS-R, emotion2vec+) | 구현됨, 정식 평가 미완 |
| 감정 데이터셋 매니페스트 (train 29,476 / val 3,569 / test 3,620) | 완료 |
| 상담 도메인 매니페스트 (`data/manifests/consultation.jsonl`) | 비어 있음 |
| 감정 모델 품질 | emotion2vec+ frozen head가 유일한 사용 가능 베이스라인 (val macro-F1 **0.240**, ECE 0.078) |
| XLS-R 로컬 스모크 (full / last-4 / LoRA-last8-qv) | 3종 모두 단일 클래스(surprise) 붕괴, macro-F1 0.0357 — 로컬 재시도 중단 |
| RunPod 전면 파인튜닝 실험 | 설계 + 오케스트레이션 코드가 `feat/runpod-xls-r-full-finetuning-design` 브랜치에 존재, **실행 전** |
| Gemini / 응대전략 / 요약 provider | 미구현 |
| 골드 평가셋 · 캘리브레이션 · 통합 벤치마크 러너 | 미착수 |
| 프론트엔드 대시보드 · HTML/PDF export | 미착수 |

즉 **파이프라인은 서 있고, 감정 품질과 사용자 화면이 남아 있다.** 8주 로드맵은 W1(설계~코어~감정 1차 실험, 완료)과 W2(RunPod 전면 파인튜닝, 진행 중)를 지나 W3~W8에서 이 두 축을 순서대로 닫는다.

W1의 핵심 발견은 **XLS-R 로컬 스모크 3종이 모두 단일 클래스로 붕괴**했다는 것이고, 그 판정이 W2의 원격 GPU 실험을 만들었다. 전체 여정은 로드맵 문서에 주차별로 정리되어 있다.

## 저장소 규칙

원본 데이터셋, 통화 오디오, 자격증명, 생성된 리포트, provider 페이로드는 절대 커밋하지 않는다. `data/` 아래 런타임 산출물은 전부 Git 무시 대상이다. 특히 licensed corpus 또는 사용자 제공 Gold에서 계산한 case ID·전사·길이·집계 지표·교육용 재구성도 public repository에는 넣지 않는다. 공개 저장소에는 코드, synthetic fixture, 그리고 원본 데이터를 재배포하지 않는 실행 절차만 둔다.
